START IN — CODEX 최종 범위 다이어트 + 3개월 팀프로젝트 대비 명령서 v4
기준일: 2026-09-26
기준 소스: 현재 Project.zip 실제 코드
목적: 승인된 시안을 절대 기준으로 두고, 기존 구현이라도 불필요하면 삭제하며, 3개월 뒤 소규모 팀프로젝트에 실제 도움이 되는 기능만 남기거나 추가한다.
중요: 이 지시문은 이전 START IN 확장/KEEP 지시보다 우선한다.

======================================================================
0. 가장 중요한 원칙
======================================================================

현재 코드는 보존 대상이 아니다.
현재 코드는 "검토 대상"이다.

이미 구현되어 정상 작동한다는 이유만으로 KEEP하지 마라.

기존 route / component / endpoint / model / test / dependency / 보안코드라도
아래 기준에서 불필요하면 삭제하거나 단순화해도 된다.

단, 최상위 제약은 승인된 START IN 시안과 UX다.

우선순위는 정확히 다음과 같다.

1. 승인된 시안과 사용자 UX
2. 약 3개월 뒤 소규모 팀프로젝트 대비 학습가치
3. START IN 서비스에서의 자연스러움
4. 기존 코드

즉 "이미 만들어놨다"는 것은 유지 근거가 아니다.

1. 기능 판단 GATE
======================================================================

모든 기존 기능과 새 기능을 아래 순서로 판단한다.

[GATE A — 시안]
이 기능을 삭제하거나 단순화하면
승인된 시안의 화면, 핵심 동작, 사용자 흐름이 깨지는가?

YES:
시안이 요구하는 최소 수준으로 유지한다.

NO:
GATE B로 간다.

[GATE B — 3개월 뒤 팀프로젝트 학습가치]
이 기능이 사용자가 약 3개월 뒤 소규모 팀프로젝트에서
실제로 다시 만날 가능성이 높은 핵심 문제를 경험하게 하는가?

예:
- React 상태/이벤트
- Router
- URL query
- API 요청/응답
- validation
- HTTP error
- DB CRUD/관계
- 로그인/사용자별 데이터
- pagination
- 파일 업로드
- migration
- 외부 데이터 import
- AI API
- 환경변수
- 핵심 테스트
- 다른 PC에서 실행 재현

YES:
START IN에 자연스럽고 시안에 위배되지 않는 최소 범위만 유지/추가한다.

NO:
삭제하거나 구현하지 않는다.

[GATE C — 중복 학습]
이미 다른 기능에서 같은 학습 문제를 충분히 경험하고 있다면
기능 하나를 더 만들어 같은 기술을 반복하지 마라.

예:
여러 개의 단순 PATCH 화면을 만들 필요가 없다.
CRUD를 배우기 위해 관리자 제품 전체를 만들 필요도 없다.

[GATE D — 과잉 기술]
"실제 큰 서비스라면 필요하다"는 이유만으로 추가하지 마라.

현재 규모에서 필요하지 않으면 구현하지 않는다.

3. 기존 코드 중 반드시 유지할 핵심
======================================================================

다음은 시안 또는 3개월 뒤 프로젝트 대비에 직접 가치가 있으므로 유지한다.
단, 현재 구현이 불필요하게 복잡하면 기능을 없애지 않는 범위에서 단순화할 수 있다.

----------------------------------------------------------------------
A. React 핵심 구조
----------------------------------------------------------------------

유지:
- React/Vite
- Router
- 메인
- 공고 목록
- 공고 상세
- Header/Hero/Filter/Map/JobList/JobCard
- 검색/필터/정렬 state
- URL query와 검색상태 연결
- loading / empty / error / retry

이유:
시안의 핵심이며
React 상태 → URL → API → 화면이라는 실전 흐름을 학습할 수 있다.

----------------------------------------------------------------------
B. FastAPI + DB 경계
----------------------------------------------------------------------

유지:
- React가 직접 DB를 만지지 않는 구조
- FastAPI API
- SQLAlchemy
- request/response validation
- 정상/오류 HTTP status
- DB 실제 조회/저장

이유:
3개월 뒤 풀스택 프로젝트의 기본 뼈대다.

----------------------------------------------------------------------
C. 로그인 최소 기능
----------------------------------------------------------------------

유지:
- 회원가입
- 로그인
- 로그아웃
- 현재 사용자 확인
- password hash
- 로그인 사용자별 데이터 분리

이유:
사용자별 데이터가 있는 팀프로젝트에서 매우 흔하다.

주의:
인증/보안 자체를 별도 연구프로젝트처럼 키우지 마라.

----------------------------------------------------------------------
D. 저장공고
----------------------------------------------------------------------

유지:
- 사용자별 공고 저장
- 저장 취소
- 새로고침 후 유지

이유:
User ↔ Job 관계,
사용자별 데이터,
중복방지,
React ↔ API ↔ DB 흐름을 한 번에 경험할 수 있다.

----------------------------------------------------------------------
E. 지원현황
----------------------------------------------------------------------

유지하되 간결하게 한다.

필수:
- 공고를 MY 지원현황에 추가
- 상태 변경
- 간단 메모
- 삭제
- 사용자별 분리

상태 종류는 현재 7개가 반드시 필요한 것은 아니다.
시안/UX에 문제가 없다면 이해하기 쉬운 최소 상태로 단순화해도 된다.

이유:
저장공고와 다른 "관계 데이터 + 상태변경" 문제를 경험할 가치가 있다.

----------------------------------------------------------------------
F. 기업정보
----------------------------------------------------------------------

Header/시안의 기업정보 축을 유지하기 위해
기업목록/상세는 최소 기능으로 유지한다.

단,
기업용 관리자 서비스나 기업회원 ATS로 확장하지 않는다.

기업 상세에서 공고를 보여줄 때
전체 `/jobs`를 전부 받아 프론트에서 회사별로 거르는 현재 방식은 수정한다.

`company_id`를 backend query로 전달하거나 동등한 server-side 구조를 사용한다.

======================================================================
4. 기존 코드 중 삭제/단순화 우선 후보
======================================================================

아래는 "이미 있으니 KEEP"하지 마라.

----------------------------------------------------------------------
A. 관리자 공고 CRUD + ADMIN_API_KEY
----------------------------------------------------------------------

현재 승인된 사용자 시안에는 관리자 UI가 없고,
3개월 뒤 학습목표를 위해 별도 관리자 제품까지 유지할 필요도 없다.

따라서 다른 핵심 기능에서 사용하지 않는다면 삭제한다.

삭제 후보:
- create job admin endpoint
- update job admin endpoint
- delete job admin endpoint
- require_admin
- ADMIN_API_KEY
- 해당 기능만 위한 테스트

공고 데이터 입력 경험은 뒤의 import pipeline으로 대신한다.

CRUD 경험은 사용자/저장/지원 데이터에서도 충분히 얻을 수 있다.

----------------------------------------------------------------------
B. 프로필 이름 수정
----------------------------------------------------------------------

현재 MY의 "기본 프로필 이름 수정"은
시안 핵심도 아니고 이미 다른 기능에서 PATCH/update를 충분히 경험한다.

따라서 승인된 시안에 꼭 필요하지 않다면 삭제한다.

MY 공간은 향후:
- 저장공고
- 지원현황
- 이력서

중심으로 단순화한다.

----------------------------------------------------------------------
C. 로그인 rate limit
----------------------------------------------------------------------

현재 구현은 학습핵심에 비해 코드 복잡도를 늘린다.

이번 프로젝트 완료조건에서 제외한다.
다른 구조에 의존하지 않는다면 삭제해도 된다.

보안 기능을 많이 넣었다는 이유로 프로젝트를 복잡하게 만들지 마라.

----------------------------------------------------------------------
D. 인증 보안 부가기능
----------------------------------------------------------------------

password hash는 유지한다.

현재 cookie session 방식을 유지한다면
그 방식에 필수적인 최소 보안은 일관되게 유지한다.

예:
CSRF를 지우면서 cookie session만 남겨
오히려 구조를 불완전하게 만들지는 마라.

하지만:
- MFA
- OAuth
- 이메일 인증
- SMS 인증
- 복잡한 RBAC
- 여러 관리자 등급

은 추가하지 않는다.

즉:
"최소한으로 안전하게 동작하는 인증"까지만 한다.

----------------------------------------------------------------------
E. 테스트
----------------------------------------------------------------------

기능을 삭제하면
그 기능을 보존하기 위해 존재하던 테스트도 같이 삭제/수정한다.

테스트 때문에 불필요한 기능을 유지하지 마라.

현재 기능과 최종 범위를 검증하는 테스트만 남긴다.

----------------------------------------------------------------------
F. 준비중 기능
----------------------------------------------------------------------

시안 Header에 보이지만 이번 프로젝트에서 구현하지 않을 메뉴는
버튼/메뉴 자체는 시안대로 유지할 수 있다.

예:
- AI 취업코치
- AI 매칭
- 현직자 인사이트
- 합격 후기
- 채용 Q&A

하지만 이번 범위에서 백엔드/DB/페이지 전체를 만들지 마라.

필요하면 현재처럼 최소 "준비중" 안내만 둔다.

시안에 메뉴가 있다는 이유로 모든 제품을 실제 구현하지 않는다.

======================================================================
5. 앞으로 추가할 기능 — 정확히 이 범위
======================================================================

다음 기능은
3개월 뒤 프로젝트 대비에 학습가치가 높고 START IN에도 자연스럽다.

이 목록 밖의 큰 기능을 임의로 추가하지 마라.

----------------------------------------------------------------------
PHASE 1. Server-side pagination
----------------------------------------------------------------------

현재 검색/필터/정렬/URL query는 이미 있으므로 다시 만들지 않는다.

추가:
- page
- page_size
- total
- total_pages 또는 동등한 정보
- 이전/다음 또는 간단한 페이지 UI
- 잘못된 page/page_size validation

중요:
프론트가 전체 공고를 받은 뒤 자르는 것으로 끝내지 마라.
API가 page 단위 결과를 반환한다.

다만 현재 demo 데이터가 작으므로
검색엔진 전체를 대규모 서비스 수준으로 재작성하지 마라.

목적:
React query
→ FastAPI
→ DB
→ page 결과
흐름 이해.

기업 상세도 `company_id` server-side filter와 함께 정리한다.

----------------------------------------------------------------------
PHASE 2. PostgreSQL 실제 사용
----------------------------------------------------------------------

현재 PostgreSQL용 설정과 compose.yaml이 이미 있다.

새 인프라를 만들지 말고 실제 연결을 검증한다.

확인:
- PostgreSQL 실행
- FastAPI 연결
- 데이터 생성/조회
- 로그인
- 저장공고
- 지원현황
- 검색

SQLite는 빠른 테스트용으로 남겨도 되지만
최종 학습기준은 PostgreSQL 실제 연결 경험이다.

----------------------------------------------------------------------
PHASE 3. DB migration
----------------------------------------------------------------------

Alembic 같은 일반적인 migration 도구를 최소 범위로 사용한다.

목적:
"DB 구조가 바뀌어도 기존 데이터를 유지하면서 변경하는 법"
을 한 번 경험하는 것.

migration 파일을 많이 만드는 것이 목적이 아니다.

실제 작은 schema 변경 1개를
upgrade / 필요하면 downgrade까지 확인하면 충분하다.

----------------------------------------------------------------------
PHASE 4. 작은 데이터 import pipeline
----------------------------------------------------------------------

현재 `demo-jobs.json` seed를 활용해
단순 seed보다 한 단계 발전된 import 흐름을 만든다.

예:
CSV 또는 JSON
→ 읽기
→ 필드 정리
→ validation
→ 중복 제거
→ Company/Job 저장
→ 성공/건너뜀/실패 결과 요약

무단 scraping 금지.

외부 실제 API가 꼭 필요하지 않다.
로컬 샘플로 전체 흐름을 경험하면 충분하다.

Spark/Hadoop 금지.

목적:
외부 데이터
→ 가공
→ DB
라는 흐름 경험.

----------------------------------------------------------------------
PHASE 5. 이력서 파일 업로드
----------------------------------------------------------------------

기존 "프로필 이름 수정" 대신
MY에 이력서 기능을 넣는 방향을 우선한다.

최소 범위:
- 로그인 사용자만 사용
- PDF
- 파일 크기 제한
- 확장자/MIME 검사
- 업로드
- 현재 파일 확인
- 교체
- 삭제
- 다른 사용자 파일 접근 차단

하지 말 것:
- OCR
- PDF 분석
- 이미지 편집
- S3/CDN
- Cloudinary
- AI 이력서 분석

파일 저장 문제 자체만 제대로 경험한다.

----------------------------------------------------------------------
PHASE 6. 실제 AI 자연어 채용검색
----------------------------------------------------------------------

START IN Hero의 AI 검색은
이번 프로젝트에서 구현할 유일한 핵심 AI 기능으로 본다.

예:
"부산에서 신입 가능하고 연봉 4000 이상인 Python 개발직"

흐름:
사용자 자연어
→ React
→ FastAPI
→ LLM API
→ 구조화된 검색조건
→ validation
→ 일반 DB query
→ 결과
→ React

LLM 역할은 자연어 해석이다.

하지 말 것:
- 모든 공고를 LLM에 통째로 보내기
- 일반 DB filter를 LLM으로 대체
- RAG
- Vector DB
- Agent
- Multi-Agent

API key는 환경변수로 관리한다.

API key가 없으면
기존 keyword 검색이 정상 동작해야 한다.

AI 호출 실패가 일반 검색까지 망가뜨리면 안 된다.

======================================================================

금지/보류:

- 실시간 알림 시스템
- RAG

- 자체 ML 추천모델
- 딥러닝 모델
- MLOps

- 결제

- 이메일 인증 시스템
- OAuth social login

- 기업회원 ATS

- 유료 공고

- 시안에 없는 새 화면을 공부용으로 대량 추가

이 기술들은 나중에
그 기술이 실제로 필요한 별도 프로젝트에서 공부한다.

START IN 하나에 모든 수업기술을 넣지 마라.

======================================================================
7. Docker / CI는 완료조건이 아니다
======================================================================

현재 PostgreSQL 실행에 compose가 이미 있으므로
DB 실행용 compose는 유지해도 된다.

하지만:
Frontend / Backend / DB 전체를
복잡한 Docker 구조로 다시 묶을 필요는 없다.

GitHub Actions CI도 이번 프로젝트의 필수 완료조건이 아니다.

핵심 기능을 모두 끝내고도
코드가 단순하게 유지되며 시간이 남는 경우에만
`frontend build + backend pytest`
정도의 최소 CI를 선택적으로 추가할 수 있다.

CI를 위해 프로젝트를 복잡하게 만들지 마라.

======================================================================
8. 코드 가독성 — 사용자가 나중에 해체공부한다
======================================================================

사용자는 완성본을 AI 없이 처음부터 외워 쓰는 것이 목표가 아니다.

목표는:
- 코드 읽기
- 기능 흐름 찾기
- AI가 만든 코드 검수
- 필요한 곳 수정
- 오류 원인 찾기
- 다른 프로젝트에서 같은 구조 알아보기

따라서 코드는 다음 원칙을 따른다.

- 평범하고 읽기 쉬운 구조
- 불필요한 abstraction 금지
- wrapper 남발 금지
- helper/utility 남발 금지
- 자체 framework 금지
- dependency 최소화
- 같은 기능을 여러 계층으로 의미 없이 분해하지 않기
- 죽은 코드 제거
- 삭제된 기능의 route/model/test/dependency도 같이 정리

코드를 따라가면 다음 흐름이 보여야 한다.

[검색]
사용자 입력
→ React state
→ URL query
→ API
→ FastAPI
→ DB
→ response
→ 화면

[로그인/저장/지원]
사용자 행동
→ React event
→ 인증된 API
→ 사용자 확인
→ DB 관계데이터
→ response
→ 화면

[파일]
파일 선택
→ React
→ FastAPI upload
→ validation
→ 저장/metadata
→ MY 화면

[AI 검색]
자연어
→ React
→ FastAPI
→ LLM 구조화
→ validation
→ DB query
→ 결과

1. 검색/필터/정렬/pagination

4. 로그인

13. 추천검색어가 FilterPanel을 변경하지 않음

최종 범위에 테스트를 맞춘다.

11. 작업 시작 전에 현재 코드를 먼저 다이어트한다
======================================================================

새 기능부터 추가하지 마라.

먼저 현재 프로젝트 전체를 검사하고
아래 세 그룹으로 실제 분류한다.

A. KEEP
시안 또는 핵심 학습에 필요.

B. SIMPLIFY
기능은 필요하지만 현재 구현이 과함.

C. DELETE
시안에도 필요 없고,
3개월 뒤 팀프로젝트 대비에도 학습가치가 낮거나
이미 다른 기능에서 같은 문제를 충분히 경험함.

그 후 실제로 SIMPLIFY / DELETE를 수행한다.

사용자에게 다시 허락을 묻지 마라.
이 문서가 삭제/단순화 권한이다.

단,
승인된 시안이 깨질 수 있는 변경은 하지 않는다.

삭제 후:
- build
- backend tests
- 핵심 E2E
를 실행해 기존 핵심 흐름이 살아있는지 확인한다.

16. 최종 판단문
======================================================================

기존 코드는 자산이지만 성역이 아니다.

승인된 시안을 지키면서,
3개월 뒤 팀프로젝트에 도움이 되는 최소한의 실전 문제만 남긴다.

START IN은 모든 기술을 넣는 전시장이 아니라,
사용자가 3개월 뒤 실제 프로젝트 코드를
읽고, 판단하고, 수정하고, 검증할 수 있게 만드는 훈련장이다.
